The playground

Every endpoint here hits my real local Firecrawl at localhost:3002 — edit the request, hit Run, and a 🟢 REAL NETWORK CALL badge (HTTP status · latency · bytes · a unique id that changes every call) marks every genuine round-trip. Endpoints that need cloud-only engines fall back to a clearly-labeled 📋 sample, so the demo never breaks. Start with the four ideas, then the Schema Lab.

① One base, two verbs

Everything is POST https://api.firecrawl.dev/v2/<thing> with Authorization: Bearer fc-…. Some endpoints answer inline (you get data back). Some answer with a job id you poll with GET …/<id>. That split is the whole mental model — see Sync vs async.

② formats = what you want back

formats: ["markdown","html","links","screenshot","summary", {type:"json", schema}, {type:"changeTracking"}]. You ask for the shapes you need; Firecrawl fills only those. markdown is the default and the product.

③ Structured extraction = schema

Instead of markdown, you hand Firecrawl a JSON Schema describing the fields you want, and an LLM fills it from the page. No schema → it free-forms from a prompt. This is the Schema Lab.

④ Heavy work is async

A single page is fast → returned inline (/scrape). Crawling a whole site, or running an LLM over many pages (/extract), takes seconds-to-minutes → so the API hands you an id in <1s and does the work in a background worker you poll.

Sync vs async — the part that confused you

This is the one thing to internalize. Same company, two response styles. Press Send on each lane and watch what comes back.

🧩

Plain English: "sync" = the HTTP connection stays open while Firecrawl does the work, and the finished data comes back in that one response. "async" = Firecrawl can't finish in one request (too slow), so it immediately says "started, here's your ticket number (id)" and you call back later to ask "done yet?" until it is. That callback-asking is polling.

🟢 /scrape — synchronous

one page · ~1–4s · data inline
POST /v2/scrape  { url }
connection held open… engine fetches + renders the page
HTML → clean markdown (the transformer pipeline)
200 { success, data: Document } — finished markdown in this same response
No id, no polling. You asked, you waited a couple seconds, you got the document. One round trip.

🔵 /extract — asynchronous

many pages + LLM · seconds–minutes · id then poll
POST /v2/extract  { urls, schema }
controller validates → mints uuidv7 → saves status:"processing" to Redis → enqueues job
200 { success, id } returned in <1s — no data yet
GET /v2/extract/:id → { status:"processing" }  (worker still chewing)
GET /v2/extract/:id → { status:"processing" }  (poll again…)
GET /v2/extract/:id → { status:"completed", data:{…} } ✓
The id is your ticket. You keep calling Poll until status flips to completed. Then the data is there.
🎯

Why the split exists: a worker can only hold an HTTP connection open so long before it times out and ties up resources. One page fits in that budget, so /scrape is sync for the best DX. But an LLM extraction across many URLs, or a 5,000-page crawl, can't — so the controller returns an id in <1s and a background worker does the slow part. /scrape uses skipNuq:true to bypass the very queue that /extract and /crawl rely on.

The async response, verbatim from extractController
// returns IMMEDIATELY — note: no markdown, no json, just the ticket
{ "success": true, "id": "0192f3a1-7c4e-7abc-...", "urlTrace": [] }

And the one hard rule baked into the controller: pass agent.model: "v3-beta" and it rejects with 400 → "Use the new /agent endpoint instead." That's the fingerprint that /extract's agent param is the legacy FIRE-1 path, while v3 autonomy graduated to its own /agent endpoint.

The #3300 trap (what my Zod-v4 fix resolves): you usually write the schema as a Zod object in code (z.object({ name: z.string() })) and the SDK converts it to the JSON Schema above. In Zod v4, the converter (tryZodV4Conversion) walked schema.constructor.prototype.constructor looking for toJSONSchema — but in v4 that's a module-level export, not a prototype method. The walk returned null, it fell through to the v3 lib, and shipped an empty {"$schema":"…draft-07"} stub → the API had no fields → result.json came back undefined. A silent types-vs-runtime lie. The fix: import { toJSONSchema } from "zod/v4" and call it directly.

scrape-quality · an LLM-readiness score for a scrape — grade(doc)
examples/scrape-quality/src/index.ts · grade(doc) → { score, rating, summary, dimensions, findings }

A pure scorer for how usable a scrape is to an LLM. Premise: today's success gate ("markdown isn't empty") is too weak — and a single high-severity finding caps the grade. The real grade() composes six scorers (in src/scoring/*) and an optional metric-anchored LLM judge (src/judge.ts):

  • structureFidelity — headings/lists survive HTML→md
  • tableCodePreservation — tables & code intact
  • boilerplateNoise — nav/cookie/footer signal-to-noise
  • tokenEfficiency — tokens spent vs content delivered
  • inlineGlue — the #3583 glued-token detector
  • extractionIntegrity — round-trips a schema (optional)

A high-severity finding caps the letter grade (correctness dominates — one fatal flaw isn't averaged away). The inline demo below is a simplified taste of those scorers.

const doc = await firecrawl.scrape(url, { formats: ["markdown","html"] });
const q = grade(doc);
q.rating;     // "C"
q.findings;   // [{ code:"INLINE_GLUE", severity:"high", evidence:"FunktionalFunktional" }, …]
